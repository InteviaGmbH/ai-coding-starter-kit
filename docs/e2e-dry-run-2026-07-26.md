# End-to-End-Testlauf: PROJ-1 bis PROJ-12 (2026-07-26)

> Manueller, vollständiger End-to-End-Testlauf mit echten Accounts gegen das echte Supabase-Projekt (nicht Teil der permanenten Regression-Suite unter `tests/` — die dort verwendeten Playwright-Skripte waren Einweg-Diagnosewerkzeuge und wurden nach Abschluss wieder entfernt).

## Ziel
Bislang war jede QA-Runde seit PROJ-2 auf Code-Review + gemockte Vitest-Tests beschränkt, da kein aktives Testkonto mit echten Daten existierte (durchgängig als Coverage-Lücke dokumentiert). Dieser Testlauf sollte diese Lücke einmal vollständig schliessen: reale Testdaten anlegen (eine Gemeinde, ein Dafinex-Kandidat, eine offene Anfrage) und den kompletten Kernprozess einmal end-to-end durchspielen.

## Testdaten
- 1 Gemeinde (`E2E Test Gemeinde <timestamp>`), angelegt durch einen manuell per SQL zum `super_admin` befördeter Testaccount
- 1 Gemeinde-Ansprechpartner-Account (Selbstregistrierung, durch den Admin freigeschaltet und der Gemeinde zugeordnet)
- 1 Dafinex-Kandidat (Selbstregistrierung, `source_type: dafinex`, Fähigkeiten „Sozialarbeit, Deutschkenntnisse", Region „Zürich"), durch den Admin freigeschaltet
- 1 Personalanfrage der Gemeinde („Sozialarbeiter:in", Region „Zürich", passender Zeitraum)

## Durchgespielter Prozess
Anfrage erstellen (Gemeinde) → als geprüft markieren (intern) → Kandidat vorschlagen (intern) → Vorschlag freigeben (intern) → Vorschlag annehmen (Gemeinde) → Einsatz anlegen (intern) → Status „akzeptiert" → Vertrag generieren (Upload) → Status „aktiv" → unterschriebene Vertragsversion hochladen → Status „abgeschlossen" → Aktivitätenprotokoll und Benachrichtigungen auf beiden Seiten (intern + Gemeinde) verifiziert.

**Ergebnis: Der komplette Prozess funktioniert durchgängig wie spezifiziert — von der Anfrage-Erstellung bis zum abgeschlossenen Einsatz inklusive Vertrag.**

## Gefundene und behobene Bugs
Dieser Testlauf hat zwei reale Bugs aufgedeckt, die keine der vorherigen Code-Review-QA-Runden finden konnte — beide wurden noch im selben Durchgang behoben:

### PROJ-8 BUG-3 (High): Gemeinde sah „Unbekannt"/„—" statt Kandidatendetails
- **Ursache:** RLS-Policy `candidates_select` (PROJ-1) erlaubte nur internen Rollen und dem Kandidaten selbst Lesezugriff auf `candidates` — für die Gemeinde existierte kein Zweig. Der Join auf der Vorschlagsliste (`/municipality/requests/[id]/proposals`) lieferte dadurch für jeden Kandidaten `null`, was durch die bereits vorhandene Fallback-Logik stillschweigend als „Unbekannt"/„—" angezeigt wurde.
- **Fix:** Neue Policy `candidates_select_municipality_proposed` (Migration `20260726140000`) — Gemeinde darf einen Kandidaten lesen, sobald dessen Vorschlag zu einer ihrer Anfragen „freigegeben" oder später ist.
- Details: siehe `features/PROJ-8-gemeinde-interview-annahme.md`, Abschnitt „Post-Approval-Regression".

### PROJ-12 BUG-1 (High): Aktivitätenprotokoll zeigte immer „Noch keine Aktivitäten."
- **Ursache:** `activity_log` hat zwei Fremdschlüssel zu `profiles` (`actor_id`, `created_by_id`). Das ursprüngliche implizite PostgREST-Embedding (`actor:profiles(...)`) war dadurch mehrdeutig und schlug mit `PGRST201` fehl — der Code prüfte den `error` nie, wodurch die Liste einfach leer erschien, unabhängig von der tatsächlichen Datenlage (46 reale Einträge vorhanden).
- **Fix:** Embedding entfernt, stattdessen eine separate Lookup-Query auf `profiles` (gleiches Muster wie bereits in PROJ-7 für `proposedByName` verwendet) — reiner Anwendungscode-Fix in `src/app/internal/activity/page.tsx`, keine RLS-/Migrationsänderung nötig.
- Details: siehe `features/PROJ-12-aktivitaetenprotokoll-basis.md`, Abschnitt „Post-Approval-Regression".

## Wichtige technische Erkenntnis
Beide Bugs traten an derselben Art von Schwachstelle auf: **RLS-blockierte oder mehrdeutige Datenbank-Joins liefern in PostgREST/Supabase keinen Fehler an die Anwendung, sondern still `null`** — und wurden durch bereits vorhandene defensive Fallbacks (`?? "Unbekannt"`, `entries ?? []`) im Code vollständig maskiert. Reine Code-Review-QA ohne echte Daten kann diese Klasse von Bug grundsätzlich nicht finden, da der Code syntaktisch korrekt aussieht. Nur ein Testlauf mit echten Datenbankzugriffen deckt sie auf.

## Bekannte Einschränkungen dieses Testlaufs
- Es wurde nur der „Happy Path" durchgespielt (keine Fehlerfälle, keine parallelen/konkurrierenden Aktionen, kein Ablehnungs-Pfad)
- Getestet nur in Chromium, nicht Mobile Safari/Firefox
- Playwright-Timing mit dem Next.js-Dev-Server (Erstkompilierung neuer Routen, `networkidle` mit aktiver HMR-Websocket-Verbindung, Hydration-Race nach hartem Redirect) erforderte grosszügige, teils mehrfach nachjustierte Timeouts — reine Testinfrastruktur-Erkenntnis, kein App-Bug

## Aufräumen erforderlich: Testdaten im echten Supabase-Projekt
Durch mehrere fehlgeschlagene Iterationen während der Skript-Entwicklung wurden zusätzlich zur letzten erfolgreichen Kombination **weitere Test-Gemeinden, Test-Accounts (`@dafinex-test.ch`) und zugehörige Anfragen/Vorschläge/Einsätze/Verträge** im echten Supabase-Projekt angelegt. Diese sind harmlos (klar als `E2E Test ...` / `e2e-*@dafinex-test.ch` erkennbar), sollten aber vor einem echten Pilotbetrieb bereinigt werden. Empfehlung: im SQL Editor gezielt nach `email like 'e2e-%@dafinex-test.ch'` (profiles/auth.users) bzw. `name like 'E2E Test Gemeinde%'` (municipalities) filtern und samt abhängigen Zeilen löschen, oder das Projekt vor dem Go-Live einmal komplett zurücksetzen.
